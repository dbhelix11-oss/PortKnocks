Channel Signaling: What We Wanted, Why It Broke, and the Fix

A worked example of how a knock-based, TOTP-style (Time-based One-Time Password) authorization scheme was extended to trigger multiple different actions — and a cryptographic mistake that got caught before it shipped.

1. Recap: how the base system derives a knock sequence

The existing client and server agree on a shared secret key (32 random bytes, generated once, copied to both sides). Time is divided into fixed-length windows — T = 30 seconds each — and a time counter just counts how many windows have elapsed since the Unix epoch: 

time_counter = floor(unix_time / T)

That counter is fed into HMAC-SHA256 together with the secret key, producing a 32-byte digest. The digest is sliced into 2-byte chunks, and each chunk becomes one port number (via modulo the configured port range): 

digest   = HMAC-SHA256(secret, time_counter)
port[i]  = PORT_LOW + (uint16(digest[2i : 2i+2]) mod (PORT_HIGH - PORT_LOW + 1))

2. The goal: multiple signal "channels"

The idea on the table: instead of the knock sequence only ever meaning "open the port," support several distinct, equally unforgeable sequences — 11 in total. Channel 0 keeps meaning "open the port" (unchanged). Channels 1 through 10 each trigger a different pre-configured action behind the firewall, entirely without needing a connection back to the client (fire-and-forget, matching how a knock already works).

3. The original idea: shift the time counter

The proposed mechanism was to reuse the existing formula, but feed it a deliberately offset time counter per channel — e.g. channel +2 would compute HMAC(secret, time_counter + 2) instead of HMAC(secret, time_counter). Ten channels, ten fixed offsets (five in each direction), no change to the hash input's shape — just a predictable "stairstep" applied to the one number already going in.

4. Why that's broken: aliasing

The problem Today's derivation is a function of exactly one thing: f(W) = HMAC(secret, W), where W is the time counter. Shifting the input doesn't create a second function — it just evaluates the same f at a different point. So "channel +2, evaluated right now at window W" is f(W+2) — and that is exactly the value that channel 0 will legitimately produce two windows from now. Same 32 bytes, same derived ports.

This isn't a matter of picking a "safer" offset. f is one function; shifting where you sample it never leaves the line it's already defined on. Every offset aliases with some other real moment in channel 0's own timeline — some are seconds away (colliding with the server's existing ±1-window clock-skew tolerance), some are further out, but none are safe, because the aliasing is structural, not a matter of degree.

5. The fix: a second, independent input

The fix Give the hash two genuinely separate inputs instead of one shiftable one — a dedicated channel_id byte, concatenated onto the message rather than added to the time value: 
digest = HMAC-SHA256(secret, time_counter || channel_id)

|| means byte concatenation — glue the two pieces together into one longer message before hashing. Now think of the derivation as a 2D grid instead of a 1D line: rows are time windows, columns are channels.

Byte layout

Why this actually fixes it HMAC treats its whole input as one opaque blob. time_counter || 0 and time_counter || 3 are two completely different messages as far as the hash is concerned — there's no "shift by 3" relationship connecting their outputs the way there was between f(W) and f(W+3) in the old, single-input version. That's the formal meaning of calling HMAC a PRF (see glossary): a family of functions indexed by whatever you feed in besides the key, where different indices give statistically unrelated outputs.

7. Glossary

HMAC (Hash-based Message Authentication Code)
A function that mixes a secret key into a hash so that only someone holding the key could have produced that output for a given message.
PRF (Pseudorandom Function)
The formal property HMAC has: indexed by a key, its outputs are indistinguishable from random unless you hold that key.
Digest
The fixed-size output of a hash function — here, 32 bytes from SHA-256.
Byte / big-endian
A byte is 8 bits, one number 0–255. "Big-endian" means the most significant byte of a multi-byte number comes first, left to right.
Concatenation (||)
Gluing two byte sequences end-to-end into one longer sequence, with no other combination or math involved.
Aliasing
Here: two different-looking inputs (a shifted time value under one channel vs. a later real time under another) producing the exact same output, because they were never independent to begin with.
Replay (attack)
Reusing a previously observed, valid message again later to trigger the same effect a second time, without knowing the underlying secret.
Nonce
A number used once — a value included specifically to make an otherwise-identical message unique, so it can't be replayed. Not used in this fix (the channel_id isn't a nonce; it's a permanent per-channel identifier).
